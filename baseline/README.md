# Timber 第一阶段：可检查的离线基准

这个独立工作副本重放一项已存档的面板背衬修正：从原始库存、已有分配、构件几何和装配关系，重新生成候选方案、切割账本、装配图与分析输入。

**离线检查通过不表示结构承载力通过。** 当前程序不运行 Rhino、Grasshopper、Karamba 或 LLM，不会更新原项目的活动指针。

## 运行

需要 Python 3.10+，仅使用标准库，无第三方 Python 依赖。

```powershell
# 安装了 uv 的当前电脑
.\run.ps1
.\run.ps1 -Test

# 其他电脑已有 Python 时
python run.py
python -m unittest discover -s tests -v
```

读取 `results/baseline/verification.json` 看完整结论。正常案例返回退出码 0；失败返回 1，并更新 `run-status.json`。输出目录可能保留前次文件，必须以当前 `run-status.json` 和 `verification.json` 为准。

## 这次新增和修复了什么

1. 从原交易检查点恢复缺少的输入，复制到 `case/`，并记录原始来源与 SHA-256。三个关键检查点与原交易清单哈希一致。
2. 库存分配函数接收显式的库存和分类数据，移除运行时对 H 盘活动路径的读取。
3. B 方案虽然库存可满足，但其分析和装配适配未完成，现在排名不可选、直接调用也明确拒绝。C 同样不可执行。没有把 B 修复成完整可用方案。
4. 新增独立验证器，检查输入版本、中心线与长度、库存身份和截面、切割与锯缝、可用区间、面板声明路径、分析成员、荷载守恒、已有分配保持及历史文件关联。
5. 排名输出符合严格 JSON，缺失指标写为 null，避免 Infinity。
6. `scripts/finalize_agent_correction_loop.py` 提供离线检查入口，替代直接写入 PASS 并提交活动指针的行为。未经修改的原脚本放在 `original-code/` 供比较，不作为执行入口。
7. 原 `allocation_revision_binding.py` 保留既有逻辑；新增测试验证标签重绑定、实体长度变化拒绝、旧结果摘要拒绝。

## 已验证的基准结果

- 本轮 19 项测试通过，其中 12 个记录化错误注入场景均被拒绝；正常案例通过 10 项离线检查，5 项工程/实时证据保持 UNKNOWN。
- 新目录运行通过，文件访问审计禁止读取原项目路径；验证报告与基准逐字节一致。
- 新增 15 个构件，来自 10 个余料来源，共约 8,306.208 mm。
- 要求、选中方案 ID、切割账本、分析 plan 和面板荷载与固定存档一致。
- 5 个原缺失面板的声明路径连接到现有宿主；17 个面板的载荷对象共约 1.093715 kN，未施加量为 0。
- 分析输入包含 275 个节点，原 34 个支座定义保持不变。
- 原始库存身份仍是快照记录身份，尺寸仍可能来自卖家标注，没有被提升为实测或结构等级证据。

## 如何理解 PASS / FAIL / UNKNOWN

`offline_replay_status: PASS` 表示本案例规定的离线一致性检查通过。`accepted_for_offline_replay` 只允许接受离线重放结果。

`engineering_approval: UNKNOWN`、`approved_for_construction: false` 保持明确：材料等级与强度、节点承载力、基础、实体净空和本次实时结构求解都没有完成验证。

历史 Karamba 数值只在输入/计划/荷载与固定存档匹配时展示，标为 `HISTORICAL_NOT_RECOMPUTED`。原结构结果没有记录完整的求解输入签名，本次导入哈希只能证明文件关联与一致性，不能补造当年的求解绑定。

## 错误注入

测试包括正常基准与以下错误场景：未知库存 ID、重复消耗同一区间、重叠切割、缺失面板接收关系、库存改短或改长、截面错误、旧交易结构结果、分析输入改动、分析成员缺失、面板自重缺失、已有分配被更改。

同时检查 B 不能被伪造排名选中或直接执行、严格 JSON、工程状态保持 UNKNOWN，以及冻结分配重绑定规则。

机器可读错误结果见 `results/fault-injection.json`。这些错误在内存副本中注入，固定案例文件没有被篡改。

## 适用范围与下一步

### 第二阶段：材料长度变化受控实验

**后续进展：** 原方案与替换候选已在 Rhino 内完成 Karamba 实际求解，见 `karamba-comparison/RESULTS.md`。该目录保存独立输入、运行脚本、新求解证据与对照报告。以下第二阶段报告保留其当时的离线状态；新的求解证据单独存放，不回写旧报告。测试新增 7 项求解证据检查，共 43 项。

运行 `python run_changes.py`，或在当前机器运行 `.\run.ps1 -Changes`。
打开 `results/change-experiment/report.html` 查看三个场景的结果与 SVG 对照图。

- 已知旋转和平移的两个合成端点，长度不变：保留全部分配；没有执行配准或姿态估计。
- 库存 `119600_001` 从 4267.200 mm 缩短至 4058.278 mm：原 900 mm 横向支撑切割超界，锁住其余 14 个新增构件的切割及锯缝，只重新分配这 1 个构件。
- 端部缺失：保持原库存与分配，输出 NEEDS_EVIDENCE。

缩短场景找到余料 `119270_009`，截面从 95.25 × 146.05 mm 变为 19.05 × 88.9 mm。
这只是长度与账本可行的替换候选，**不代表较小截面满足承载力或净空要求**。程序完整重建分析输入，输出 REQUIRES_NEW_SOLVE，未沿用历史位移结果。

实现复用了用户原有的余料优先贪心分配器及分析适配器；新增观测分类、变化版本、切割预留、局部修复和新阶段检查。不会重新比较 B/C 拓扑，不保证全局最优。独立验证在 revision 模式检查新输入，并明确把历史关联标为 NOT_APPLICABLE；原 frozen 模式的严格基准检查保持不变。

范围限定为尚未加工的新增 A 方案、固定原点的长度变化和精确合成观测。若缩短触及既有或未明确可用的材料区间，输出 UNSUPPORTED_SCOPE；带非零不确定性的测量暂时输出 NEEDS_EVIDENCE。根余料区间不会因长度增长而自动扩展。材料等级、节点承载力等仍是 UNKNOWN。

分配只重算受影响构件；分析导出完整重建，验证覆盖完整新阶段。没有执行实时结构求解，也没有实现结构求解器内部的增量计算。

每个场景目录有 `observation.json`、`report.json`、`run-status.json`。成功生成新阶段时还输出新分配、图、分析框架、荷载和 `solver-request.json` 输入摘要。摘要标识待求解请求，不是新求解结果或历史求解证明；以本次 run-status 的 `stage_available` 为准，勿复用目录里旧的阶段文件。

测试现在共 36 项（第一阶段 19 项，第二阶段 17 项），包含锁定切割/锯缝、修改越界、证据不足、输入过期、无候选池和新账本损坏。无候选池测试在预留边界注入空池，未声称真实库存无解。运行 `.\run.ps1 -Test` 可复核。

下一步再接真实 DiffCheck 测量及有输入绑定的 Karamba 新求解；目前不把受控实验称为实测复现。

### 第一阶段范围说明

当前是一个固定案例的可复现研究基准，仅执行水平背衬条与回接构件的方案 A。排序目标沿用原项目，没有声称已经解决多目标资源优化；也没有声称支持任意朝向、任意装配类型或自动识别材料缺陷。

固定案例的输入被修改时会拒绝复用。下一阶段应在新案例版本中接入测量证据，重新生成与验证分配，并让旧结构结果保持失效状态，直到产生有输入签名的新求解结果。

可移植性验收由 `tools/verify_portability.py` 完成：复制到新目录，在文件访问审计中禁止读取新目录与 Python 运行时以外的文件，再比较验证报告是否逐字节一致。该工具只允许在新的目标目录执行，避免覆盖上次验收证据。

源码归属：生成、分配、装配适配和版本绑定源于用户提供的 Timber 项目；本次新增的是复现封装、执行边界与验证。原项目的 Cubbyhouse / ArchSim 等参考关系继续保留，不能把本包描述为独立发明这些上游方法。
